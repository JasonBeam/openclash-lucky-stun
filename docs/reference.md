# 技术说明与常见问题

本文件解释这套方案背后的机制、验证方法和失败条件。

标注约定：

- **【实测】**：在本环境做过对照实验，有计数器、抓包或外部探测等证据（原始输出见 [证据附录](evidence.md)）；
- **【机制分析】**：与现象一致的解释，但没有逐包证明，可能是主因也可能是并发因素。

本方案只覆盖 **IPv4 TCP**。不同 OpenClash 版本、不同接管模式（TUN / TPROXY）不保证适用。

---

## 1. 为什么 DIRECT 不等于绕过防火墙

【实测】在 Clash 里给相关域名设成 `DIRECT` 后，连接仍然不按预期走。表现包括：客户端指定的目标 IP 被忽略、源端口关系改变。

【机制分析】原因分三层：

1. **接管在策略之前**：防火墙先把匹配的 TCP 流量 REDIRECT 到 Clash 内核，`DIRECT` 只是内核内的选择，连接已经被接管。
2. **内核重新拨号**：内核用自己的 socket 发起新连接，源端口、目标地址可能与应用原连接不同。
3. **SNI 改写目标**：开启 `override-destination` / `force-dns-mapping` 时，内核按域名重新解析后拨号，客户端钉住的 IP 失效。

因此正确的绕过点是 **nftables 链中的 `return`**，而不是 Clash 里的策略。

---

## 2. Fake-IP / REDIRECT 对连接行为的影响

【实测】几个容易踩坑的现象：

| 现象 | 观察 | 含义 |
| --- | --- | --- |
| 本地解析到 `198.18.x.x` | NAS 上 `getent hosts <域名>` 返回 Fake-IP 段地址 | 应用拿到的是假地址，真实解析在内核里做 |
| `curl --resolve` 指定 IP 无效 | 指定 `1.1.1.1` 与 `203.0.113.7` 结果完全相同 | 内核按域名重解析后拨号，目标 IP 被忽略 |
| `time_connect` 恒为毫秒级 | `0.0006s` 完成 TCP 握手 | 握手指向本机内核，不能用来判断远端质量 |
| 只有 TTFB 可信 | `time_starttransfer` 才是真实往返 | 任何基于 connect 计时的测速都会失真 |

**结论**：在 OpenClash 开启的环境里，不要用「TCP connect 延迟」判断线路好坏，也不要用 hosts 钉 IP 的方式优化走代理的流量。

---

## 3. STUN 拿到映射 ≠ 入站成功

Lucky 的 STUN 只做一件事：向 STUN 服务器探测，让运营商 NAT 建立一个「内网端口 ↔ 公网地址:端口」的映射。

它不负责：

- 路由器把入站流量转发给 NAS（需要 UPnP 或手动端口转发）；
- 运营商放行这个公网端口（NAT 行为决定）；
- 后端服务正常响应。

所以面板显示「已获取公网地址」只能证明第一段成功。

---

## 4. 为什么需要正确的 UPnP / 端口转发

STUN 打出来的是**出站方向**的映射；外网访问是**入站方向**，需要一条静态转发把「WAN 端口」送到「NAS 监听端口」。

【实测】路由器 UPnP 建立映射后，`upnp_forward` 出现放行规则、`upnp_prerouting` 出现 DNAT 到 NAS 的规则；两者同时存在才完整。

常见错误：

- 只做了 `upnp_forward`，没做 DNAT；
- 映射指向了错误的 IP 或端口；
- 同时开了 UPnP 和手动转发，产生冲突；
- WAN 端口与 NAS 监听端口混为一谈。

---

## 5. 为什么必须核对 nftables 规则位置

nftables 按规则顺序匹配。绕过规则必须排在 REDIRECT 之前，否则流量先进内核，`return` 再也不会被看到。

【实测】用 `nft insert rule` 插到链首，并用 `nft -a list chain inet fw4 openclash` 确认 handle 顺序。

如果 OpenClash 重载后重建链，规则可能被清掉；需要确认自定义脚本在其启动/重载流程中确实被执行。

---

## 6. 为什么不能只看 counter 判断成功

`counter` 增长只说明「有包命中这条规则」，它不能说明：

- 外网能连进来（可能是入站映射缺失）；
- 运营商放行（可能只放行了别的端口）；
- 后端正常（可能 502 或错误页）；
- 长期稳定（端口会变）。

正确的顺序是：counter → UPnP 映射 → 外部连接 → 内容校验。

---

## 7. 为什么不建议随意开启 DMZ

DMZ 把 WAN 入站**全部** DNAT 给 NAS：

- 解决不了运营商只放行当前映射端口的问题；
- 把 NAS 上所有服务暴露到公网，风险显著增加；
- 故障时无法区分是映射、NAT 还是服务问题。

只开放业务需要的端口，并给每个入口配认证。

---

## 8. 映射地址和端口会变化

【实测】同一套配置下，Lucky 记录到的公网地址与端口发生过多次变化，间隔从几分钟到几天不等。

影响：

- 普通 DNS A 记录只保存 IP，不携带端口；
- 写死在客户端或书签里的「IP:端口」会失效；
- 每次变化都要重新确认外部入口。

应对：缩短 Lucky 的重测周期、接受手动更新，或改用隧道类方案获得固定入口。

---

## 9. 修改后无法访问的排查路径

```text
外网访问失败
├─ NAS 本地 curl 后端 → 失败：先修服务
├─ Lucky 有当前公网映射 → 没有：检查 STUN 与网络条件
├─ 路由器 upnp_forward / upnp_prerouting 有映射 → 没有：检查 UPnP 与权限
├─ openclash 链中 return 在 REDIRECT 之前 → 不在：调 insert 与脚本位置
├─ counter 增长 → 不增长：saddr/sport 写错
├─ 外部能连但内容不对 → DNAT 目标或后端地址错
└─ 以上都对仍失败 → 运营商放行/端口变化，换时间点重测
```

**规则失效的常见原因**：OpenClash 重载后链被重建、脚本没被执行、NAS 的 IP 变了、端口改了没同步。

## 10. 常见问题

**Q：为什么 443 端口做 STUN 容易失败？**
【实测】OpenClash 开启 `disable_udp_quic` 时，nft 在 input 链对 UDP 443 直接 reject；同时规则里的 `DST-PORT,443` 会把流量送进代理组。STUN 探测包到不了服务器。本方案只做 TCP，避开这个问题。

**Q：在 NAS 的 hosts 里钉了 IP，为什么没生效？**
【实测】Fake-IP + SNI 嗅探会按域名重新解析拨号，钉住的 IP 对经代理的连接无效。

**Q：测速显示延迟 0.2 ms，说明节点很快吗？**
不是。握手在本地内核完成，要看 TTFB 或实际下载。

**Q：counter 涨了，但外网还是连不上？**
说明绕过规则命中了，但入站链路没通：检查 UPnP 映射、运营商放行、公网端口是否已变化。

**Q：重启后规则没了？**
说明自定义脚本没有被调用或没有持久化。确认脚本位置、调用方式，并检查 OpenClash 重建链的时机。

**Q：能不能只让 Lucky 绕过，不影响其他应用？**
本方案按「源 IP + 源端口」匹配，不区分进程。更精细的做法需要按进程或 cgroup 匹配，本仓库未验证。

**Q：我的环境是 TUN 模式，能用吗？**
不能照搬。TUN 的接管点在设备层，绕过位置不同，需要重新分析链路。

---

## 11. 已知限制

- 只覆盖 IPv4 TCP；UDP、QUIC 未验证；
- 只覆盖 Firewall4 / nftables + REDIRECT；Firewall3 / iptables / TUN / TPROXY 不适用；
- 穿透能否成功依赖运营商 NAT 与端口放行，无法保证；
- 公网地址与端口会变化，入口不是固定的；
- 不同 OpenClash 版本的链名、脚本调用方式可能不同。
